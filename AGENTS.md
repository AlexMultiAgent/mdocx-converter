# AGENTS.md

This monorepo ships two products that share a Markdown→DOCX pipeline. **Read the sub-`CLAUDE.md` first** for architecture and exact commands; this file is a quick-ramp cheat sheet.

## Monorepo layout

| Directory | Stack | Build | Tests |
|---|---|---|---|
| `VSC-plugin-MD2Docx-Converter/` | TypeScript VS Code extension (8 modules under `src/`, ~2800 LOC) | `npm install && npm run compile && npm run package` | `npm test` — Node's built-in `node:test`, 10 files under `test/unit/`; `npm run test:e2e` — real pandoc |
| `dify-plugin-MD2Docx/` | Python Dify Tool plugin (`src/md2docx.py`, ~1310 LOC) | `python scripts/package.py --output MD2Docx.difypkg` | `pytest tests/ -v` from inside this dir |
| `scripts/sync-templates.sh` | bash | — | `bash scripts/sync-templates.sh --check` |
| `scripts/check-preset-parity.py` | python | — | `python scripts/check-preset-parity.py` — runs in CI's `preset-parity` job |

Each subdirectory has its own `CLAUDE.md` with the real architecture and command cheatsheet. Do not duplicate that here.

## Hard rules (from existing `CLAUDE.md`)

- **Commit author is `AlexMultiAgent` only.** Never add `Co-Authored-By: Claude` or any other co-author trailer to commit messages.
- **Templates: VSC plugin is the source of truth.** `VSC-plugin-MD2Docx-Converter/multi-templates/` and `dify-plugin-MD2Docx/multi-templates/` hold the **same 10 files** — `reference_{english,chinese}_{academic,technical,business,official,thesis}.docx`. They are generated by the VSC side's `scripts/build-templates.js` from one declarative style table, so regenerate them there (`npm run build:templates`) rather than hand-editing a .docx. After editing, run `bash scripts/sync-templates.sh` to copy to Dify, then commit both sides in one PR.
- **The two plugins keep their style presets in different languages** — TypeScript in `src/profiles.ts`, Python in `src/md2docx.py` — so nothing compares them automatically. `scripts/check-preset-parity.py` is that comparison: it checks every font, size, margin, line-spacing value and the template map on both sides. It needs the VS Code side compiled (`npm run compile`) and the Dify side's Python dependencies; CI runs it in the `preset-parity` job, and it can also be run by hand after changing a preset on either side.
- **Dify plugin output size budget.** The daemon rejects a plugin package whose *uncompressed* size exceeds `MAX_PLUGIN_PACKAGE_SIZE` (50 MB by default, `internal/types/app/default.go` in `dify-plugin-daemon`). The current `.difypkg` is ~140 KB compressed / ~220 KB uncompressed, so there is headroom — but a previous attempt to vendor the pandoc binary into the package was reverted for exactly this reason. Do not re-introduce it.

## Dify plugin gotchas agents miss

These are not in the README/manifest but are critical:

- **`requirements.txt` uses `pypandoc-binary` (NOT plain `pypandoc`)** which *bundles* a pandoc binary inside the pip wheel — no runtime GitHub download, no network call. `_ensure_pandoc()` just calls `pypandoc.get_pandoc_version()` to verify the bundled binary is reachable.
- **Pandoc is deliberately NOT warmed up at import time.** Spawning a subprocess before `Plugin.run()` starts the event loop can deadlock in the gevent-patched sandbox, so the first conversion pays the cold start instead.
- **Pandoc's `--metadata mainfont/fontsize/linestretch` never reaches the DOCX.** With any of the 10 bundled reference templates, `word/document.xml` and `word/styles.xml` come out byte-identical with and without the metadata — only `docProps/custom.xml` records it. The template's own `docDefaults` set the base font, so the **DOCX style override is the only layer that actually formats the document**. When you change how a document looks, change `apply_style_overrides` / `PROFILE_DEFAULTS`; `PROFILE_METADATA` is now derived from that one table, so the two cannot drift apart.
- **Pandoc runs with `--sandbox`.** It blocks URL fetches and local-file reads from the user's Markdown, so **images must be `data:` URIs**. Mermaid output is inlined that way automatically; a user's own `![](logo.png)` no longer resolves. The VS Code extension is *not* sandboxed and still resolves local files via `--resource-path`.
- **`title` is the file name, and it is sanitised.** `sanitize_filename()` replaces the characters that are illegal in a file name (`<>:"/|?*` plus control characters) with `_`, trims, truncates to 120 characters, and falls back to `"Document"`. Both the JSON `file` field and the blob `filename` carry the sanitised name.
- **`mermaid_enabled` arrives as a string.** Dify form inputs are strings, so `_coerce_bool()` treats `"false"`, `"0"`, `"no"`, `"off"`, `"disabled"`, `"n"` and `""` as False. A plain truthiness check would silently keep Mermaid **on** for `mermaid_enabled: "false"`.
- **A workflow tool node sends a boolean form parameter as the string `"False"`** (Dify stringifies the value), not `"false"`. `_coerce_bool()` lowercases before matching `_FALSY_STRINGS`, so it is handled — but that `.lower()` is load-bearing: a plain truthiness check would keep Mermaid **on** for every `mermaid_enabled: false` set in a workflow node.
- **Mermaid is capped at 50 diagrams and 32 MB of rendered PNG data per conversion**, on top of the 75s total budget.
- **Icon must exist at BOTH `dify-plugin-MD2Docx/icon.svg` and `dify-plugin-MD2Docx/_assets/icon.svg`.** The manifest's `icon:` points at the root copy; `_assets/` is the canonical location the marketplace check resolves. Keep the two byte-identical.
- **`pytest.ini` lives in `dify-plugin-MD2Docx/`, not the repo root.** Run `pytest` from inside the plugin directory or pass `cd dify-plugin-MD2Docx && pytest`.
- **`tests/conftest.py` skips the entire suite** with a `pytest.skip(..., allow_module_level=True)` if `dify_plugin` is not importable. Install `requirements-dev.txt` first.
- **Mermaid requests go to `https://mermaid.ink/img/pako:<encoded>`** (public, no auth, no rate limit). The diagram is deflated and base64url-encoded into the URL. Set `mermaid_enabled=false` in the tool call to disable for privacy-sensitive content. Documented in `PRIVACY.md` and `dify-plugin-MD2Docx/README.md`.
- **5 MB input cap.** `MAX_MARKDOWN_BYTES = 5 * 1024 * 1024` rejects oversized markdown with a structured `{"status":"error","stage":"validation"}` JSON. Above that, the Dify plugin sandbox OOMs.
- **`_strip_dangling_image_rels()`** post-processes the pandoc output to remove `<Relationship Type=".../image" Target="media/...">` entries whose target file is missing. Some reference templates have such dangling rels; without this, `python-docx` fails to open the output.
- **Three tools, 27 parameters in total.** `tools/md_to_docx.yaml` → *Markdown to DOCX* (6 params: `markdown_content`, `title`, `style_profile`, `reference_language`, `mermaid_enabled`, `mermaid_api_url`). `tools/md_to_docx_advanced.yaml` → *Markdown to DOCX (Advanced)* (those 6 plus 13 style overrides). `tools/mermaid_converter.yaml` → *Mermaid to Image* (2 params). `style_profile` enum: `academic|technical|business|official|thesis|template`. NOTE: a `type: file` param (`custom_template`) is **not exposed in any tool schema** — no published version has it — because a `file` tool parameter makes a Dify **workflow** tool node hang in `get_workflow_tool_runtime()` and never dispatch (`POST dispatch/tool/invoke` never fires; node stuck "running" until timeout). Do not re-add `file`-type params unless the plugin is only used in Agent nodes.
- **CJK ranges must be ASCII escapes.** Both plugins detect Chinese with `[\u3400-\u4DBF\u4E00-\u9FFF\uF900-\uFAFF]`. Written as literal characters the lower bound silently becomes U+8C48 and the range swallows Hangul and Yi — a Korean document then picks the Chinese template. The two characters look identical in an editor, so never retype them.
- **Test markers `slow` and `integration`** are declared in `pytest.ini`. `slow` covers the real pandoc + python-docx round-trip; `integration` covers the opt-in live Mermaid Ink check in `tests/test_mermaid_live.py`, which only runs when `RUN_LIVE_MERMAID=1` is set (it calls the public service). Everything else skips by default.

## VSC plugin gotchas agents miss

- **`tsconfig.json` compiles to `out/`, gitignored.** Don't commit `out/extension.js`; it is regenerated by `npm run compile`.
- **`.vscodeignore` whitelists `node_modules/adm-zip`** (runtime dep) and `multi-templates/*.docx` and `assets/icon.png`. Keep these in sync if you add new runtime assets.
- **The VS Code plugin has a unit suite** (`VSC-plugin-MD2Docx-Converter/test/unit/`, Node's built-in `node:test`, no framework dependency). `npm test` compiles `src/` to `out/` and runs it; CI runs the same command. The per-profile export check (`npm run test:e2e`, `test/e2e/run.js`) drives the real `pandoc` against every bundled template and **is not wired into CI** — it needs pandoc on the runner.
- **Pandoc and mmdc are discovered at runtime**, not bundled. The `checkEnvironment` command reports the binary versions, the active Mermaid renderer, the Mermaid Ink API reachability, the bundled template count and the active profile — the fastest way to debug "binary not found" issues.
- **Mermaid is local-first, API as the fallback.** With `mermaidRenderer=auto` the extension renders through `mmdc`; when the CLI is missing it falls back to the Mermaid Ink API (one notice per installation, shown before the first request), and a diagram that fails both ways stays a code block instead of failing the export. `mermaidRenderer=local` disables the fallback, `=api` skips `mmdc` entirely.
- **8 commands** are registered (see `package.json` `contributes.commands`): one generic export, 5 submenu exports (academic / technical / business / official / thesis), a Mermaid-to-image command and `checkEnvironment`. The 5 submenu commands override `styleProfile` and `referenceLanguage` regardless of user settings.
- **`paperifyMd.*` settings are legacy aliases** for `mdocxConverter.*`; `readConfigValue()` checks both. Don't remove the legacy fallback without a deprecation cycle.

## Template sync workflow (one-way, VSC → Dify)

```bash
# from repo root
bash scripts/sync-templates.sh                # copy the 10 known templates
bash scripts/sync-templates.sh --check        # CI-friendly: exits 1 on mismatch
```

The script copies 10 files by name (`reference_{english,chinese}_{academic,technical,business,official,thesis}.docx`) — the list is hardcoded, so a new template has to be added there as well. A template that is missing on the VSC side but present on the Dify side emits a `WARN` and is skipped; a template that only exists on the VSC side is not noticed at all.

## Build & verify

```bash
# Dify plugin
cd dify-plugin-MD2Docx
pip install -r requirements.txt -r requirements-dev.txt
python -c "import ast; ast.parse(open('src/md2docx.py', encoding='utf-8').read())"
pytest tests/ -v -m "not integration"        # pandoc binary comes from pypandoc-binary wheel; no network needed

# VS Code extension
cd VSC-plugin-MD2Docx-Converter
npm install
npm run compile                              # tsc -p ./
npm test                                     # compile + node:test unit suite (Node >= 22)
npm run package                              # vsce package --allow-missing-repository → .vsix
```

There is **no** `dify-plugin plugin package` step: `dify-plugin-cli` is not on PyPI. Build the `.difypkg` with `python scripts/package.py --output MD2Docx.difypkg` — see "Publishing to the Dify Marketplace" below.

## Publishing to the Dify Marketplace

The marketplace lives in `langgenius/dify-plugins`; the fork is `AlexMultiAgent/dify-plugins`. Flow: commit and push the source here first, then commit the built `.difypkg` to `AlexMultiAgent/md2docx/MD2Docx.difypkg` on a branch of the fork, then PR against `langgenius/dify-plugins:main`. **One version-update PR = exactly one `.difypkg` file.**

### The pre-check CI rejects the PR unless

- `manifest.yaml` has **`contact`** — a valid email address.
- `manifest.yaml` has a top-level **`network.domains`** list covering every host the plugin can reach (currently just `mermaid.ink`; the scanner also matches URLs quoted in a tool YAML's `human_description`).
- `requirements.txt` pins **`dify_plugin>=0.9.0`**.
- The PR body has a **`## Local validation`** section and a **`## Security and privacy notes`** section. The latter may not read "None/N/A" when the scanner found filesystem or network capabilities — disclose the temporary-file writes and the outbound host.
- The PR body is **English only** (CJK outside code blocks is rejected) and carries the info fields Author / Plugin name / Version / Source repository / Contact, both submission-type checkboxes, and a risk level.

The validators live in `langgenius/dify-marketplace-toolkit` under `toolkit/checks/*.py` — read them there for the exact rules. Check the body locally before opening the PR; a failed CI round costs ~15 min and names only one missing piece at a time.

### Packaging without the CLI

`dify-plugin-cli` is not on PyPI (404, and the Aliyun mirror has it neither), so `dify-plugin plugin package` cannot be used. `dify-plugin-MD2Docx/scripts/package.py` builds the artifact instead:

```bash
cd dify-plugin-MD2Docx
python scripts/package.py --output MD2Docx.difypkg
```

It applies `.difyignore` (keeping `.difyignore` itself in the package), sorts the entries by ASCII path, writes them with `ZIP_DEFLATED` and no directory entries, and refuses to build unless every required entry is present (`REQUIRED_ENTRIES` — manifest, `main.py`, both icons, the three tool YAMLs, the three `src/` modules). The entry **order and contents** are reproducible, but each zip entry embeds the source file's mtime, so two builds of the same tree are **not** byte-identical. Verify by unzipping the artifact and re-running the checks against the *extracted* tree (manifest fields, `_assets/<icon>`, each tool YAML's `extra.python.source`, and the SDK's `load_single_subclass_from_source`).

CI builds the package for both the minimum and the current `dify_plugin` SDK and uploads it as an artifact (`.github/workflows/ci.yml`).

### Environment notes for this machine

- `github.com` is unreachable over **HTTPS** (TCP connect times out); `api.github.com` and **SSH** work. Push over `git@github.com:...` and use `gh` for everything else.
- The upstream marketplace repo is huge — `git fetch --depth=1 --filter=blob:none` over SSH works, a full fetch does not. Creating the fork branch through the GitHub API (`git/blobs` → `git/trees` → `git/commits` → `git/refs`) avoids cloning it entirely and gives an exact one-file diff against upstream main.
- `gh` is authenticated as `AlexMultiAgent`; the GitHub MCP server is not usable for this flow (no `repo:org` / PR-creation scopes).
- A local Dify checkout runs at `D:\dify` (docker compose). Docker Desktop is often not running when a session starts — launch it and the stack comes up by itself; `plugin_daemon` restart-loops for ~30 s while Postgres initialises, then recovers. From Git Bash, `docker exec`/`docker cp` rewrite `/tmp/...` into Windows paths — set `MSYS_NO_PATHCONV=1`.
